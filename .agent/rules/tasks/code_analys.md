# code_analys

代码分析目录。各类平台代码分析、线上数据排查、逻辑验证。

## 规则

- 每个问题独立文件/目录，命名 `questionN_<简述>/`（如 `question37_sku_gross_profit/`）
- 分析时先输出结论和方案，用户确认后再改代码
- 数据样本文件只读，禁止修改
- 代码修改需标注改动点和原因
- **分析闭环必写文档**：结论确认后必须沉淀到本问题目录，便于下次复用（见下方「文档闭环」）

## 文档闭环

> 目标：本次分析结论成为下次分析的输入，避免重复踩坑、重复追字段定义。

### 何时写（强制）

| 时机 | 动作 |
|------|------|
| 开新问题前 | 先扫相关 `question*/README.md`（同平台 / 同字段 / 同链路），复用已有结论 |
| 分析中发现可复用知识 | 当场记到本问题 README「可复用」小节，勿只留在对话里 |
| 结论用户确认后 | **必须**写/更新本问题 `README.md`；未写文档视为未闭环 |
| 后续补充/翻案 | 追加到同一 README，保留日期；禁另起无关文件散落 |

方案类长文可用同目录 `*.md`（如 `enrich_erp_history_order.md`），但 README 必须有入口摘要 + 指向该文件。

### README 必含结构

```markdown
# Question N: <一句话标题>

## 问题
## 原因
## 影响
## 修复
## 可复用          ← 下次分析优先读这一节
## 关联
```

- **问题 / 原因 / 影响 / 修复**：与现有风格一致，结论先行、可核对
- **可复用**（必填，下次分析的钩子）：至少写清
  - 字段定义（平台 + 字段名 + 含义；注明「已含券 / 未含券」等易混点）
  - 数据模型关系（1:1 / 1:N、匹配键、顺序依赖）
  - 关键链路节点（表/函数/脚本路径，精确到可跳转）
  - 验证方法（样本怎么算、对比脚本、预期差多少）
  - 坑点清单（已踩过的错匹配、重复扣减、二次 UPDATE 等）
- **关联**：相关 question 目录名；无则写「无」

### 复用检查（开场 30 秒）

新分析开始前自问并执行：

1. 同平台 / 同指标以前是否分析过？→ 打开对应 README「可复用」
2. 字段定义是否已有定论？→ 直接引用，禁重新猜
3. 本问题是否会改已有链路？→ 在关联问题 README 补一句交叉引用

## 分析流程

1. **复用**：扫相关 question README「可复用」节，确认字段定义与已知坑
2. 有数据样本先读样本，理解数据结构和字段含义
3. 读代码，找到目标字段的计算逻辑
4. 手动推算预期值（有样本用样本算，没样本用逻辑推）
5. 对比预期值和实际输出，定位差异
6. 输出结论：哪行代码、什么原因、差多少
7. **沉淀**：用户确认后写/更新 README（问题→原因→影响→修复→可复用→关联）

## 注意事项

- 同名字段在不同平台含义不同（如 Shopee 的 `item_paid` ≠ Lazada 的 `item_paid`），分析前先确认字段定义
- 追踪完整数据链路再下结论，不要在中间环节停手（如：DB 字段 → 计算函数 → 聚合 → 分摊 → 最终值）
- 搞清楚数据模型再看代码（如：order item 和 escrow item 是 1:1 还是 1:N）
- 多层问题要逐层排查，不要修了一层就认为修完了
- 对话里的推算、对照表、坑点若不进 README，下次会话等于没发生过

## 代码修改

- 最小改动，不顺手重构
- **保持原文件格式**：禁改无关空格、缩进、空行、对齐、引号风格、换行风格；只改逻辑需要的行
- 写入时按原文件既有风格粘贴，**禁**整段重排或"顺手格式化"
- diff 应只含业务相关行；若出现大片空白/缩进 diff，说明改多了，应回退重做
- 改动处用注释标注原因
- **行宽（软上限）**：单行尽量不超过下面这段字段列表的长度；能放一行就一行，不要为「好看」提前拆行；仅在超出、或可读性明显变差时再换行

```text
'order_type', 'online_spu_id', 'online_sku_id', 'sku_id', 'sku_level', 'brush_or_not_int', 'purchase_unit_price', 'spu_avg_purchase_unit_price'
```
